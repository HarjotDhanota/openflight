Branch audited: `feat/clubpose-fit` @ `75d86bf` + 4 untracked files (2 spike specs, 1
segmentation spec, 1 TDD stub `tests/test_clubpose_outline_align.py` — implementation
`outline_align.py` does not exist yet, so the third spike is unstarted).

## Verdict up front

**On the right track, but one cycle late in admitting it.** The team ran the expensive
experiment (full 6-DOF silhouette IoU/chamfer pose fit on real frames) that the July
research guide's own §1C had already predicted would fail, got the predicted failure with
real numbers, wrote it up honestly, and pivoted to exactly the architecture Trackman
actually uses (fixed/prior orientation + 2D template translation, camera for location and
timing, not for solving 6-DOF orientation). The pivot is correct. The team is not yet
executing it — the two spike specs that operationalize the pivot are written but neither
has run.

## 2. Contradictions between documents, and between documents and code

**(a) §1C vs the August silhouette work — justified re-test, but a costly one, and one whose outcome had already been named.**
The July research guide states plainly (line 104): *"recovering face angle/dynamic loft markerlessly from a behind-the-ball camera to ≤2–3° is NOT achievable by any current optical method — the limiter is the vantage, not the algorithm."* The August work spent multiple days building a 4-DOF then 6-DOF IoU/chamfer fitter (`fit.py`), a metric-comparison (chamfer vs IoU), and a range-model correction — and arrived at the same conclusion with real numbers (1px = 10°, 12.7° median metric disagreement, 0/6 in-envelope). This was **not wasted in the sense of being wrong to attempt** — PR #215's real hardware, real plate scale, and real segmentation noise weren't known quantities in June, and the July claim was itself literature-sourced (INFERRED, not measured on this rig). But the outcome was foreseeable in direction if not magnitude, and the report's own §04 "Recommendation: no further effort on the objective function" is just §1C restated with evidence attached. The real mistake, if any, was not re-checking §1C before investing in a second metric (chamfer) and a 6-DOF extension once the 4-DOF version was already showing the same pathology.

**(b) The guide's own internal correction (§2.4, 2026-08-22) already pointed at the right architecture before the August spikes were written.**
"Impact location falls out of the fusion, not out of frame rate" (feasibility-verdict:100) and "impact location is NOT gated by plate scale... treat impact location as plausible on the improved single camera" (feasibility-verdict:365) — this is the same conclusion the 2026-08-28 template-alignment brief reaches independently ("Why translation-only is legitimate here... range is pinned by the radar, lie by the shaft, loft by a static prior, so the only free parameters are the two the camera measures directly"). The two documents agree; the code took roughly a week (2026-08-25 to 2026-08-28) to get from the 6-DOF fit to the translation-only design that the research doc had already justified on 2026-08-22. Not a contradiction, but a lag between the standing research and what the fitting code was doing.

**(c) `projection.py` still carries the old A0 preset and the old geometry constants — confirmed by reading, but only partially load-bearing.**
- `projection.py:100-131` (`camera_presets()`) still defines `A0` with `fx=1033.0`, `plate_scale_px_per_mm=0.656` — the wrong intrinsics named in the prompt. **This function is not called anywhere in `src/`** (only `grep` hits are its own definition and a comment in `fit.py:89` referring to "the evaluation copy" that resolves cameras by name, which lives on the other branch, not this one). So the wrong preset is present but dead in this branch — it is not silently corrupting a live result today, but it is exactly the trap the `fit.py` docstring warns about, and nothing prevents a future caller from doing `camera_presets()["A0"]` and getting 1033px fx silently.
- `projection.py:12` `CAMERA_HEIGHT_MM = 209.55` and `projection.py:11` `NOMINAL_RANGE_MM = 1_575.0` **are** live: `CAMERA_CENTER_WORLD` (`projection.py:26-27`) is built from them, and `fit.py:16-19` imports `CAMERA_CENTER_WORLD` directly and uses it for every ray-to-3D backprojection in `fit_frame`, `fit_frame_6dof`, and `fit_sequence`. The measured height for the actual session is 203.2mm (tape, confirmed in `fit.py`'s own docstring and in `tests/test_clubpose_fit_real_range_grid.py:20-21`: `CAMERA_HEIGHT_M = 0.2032`). **`fit.py`'s `measured_camera()` (fit.py:65-79) fixes fx/fy/cx/cy/plate_scale but does not touch `CAMERA_CENTER_WORLD`'s height or range**, so every 3D point the pose fitter produces is built on a camera position that is ~6.4mm too high and ~6mm too far. This is real, verified by reading, and nobody has fixed it — but given the confirmed noise floor is tens of degrees, a <0.5° geometry offset from a 6mm height error is not the binding constraint. It should still be fixed because it's cheap and it's exactly the kind of "measured vs. hardcoded" drift the report is trying to stamp out everywhere else.

**(d) Does `fit_sequence` still pin a constant range? Partially — the "radar range model, implemented" claim in the report's recommendation table is not reflected in `src/` on this branch.**
`fit.py:fit_sequence` (line ~300) defaults to `range_grid_mm=(1481.0, 1581.0, 1681.0)` — three static points centered on the ball's own range, with local refinement (`refine_range=True`) taking 50mm steps and a smoothness penalty (`d_rng / smooth_mm`, `smooth_mm=300`) that discourages large per-frame range jumps. There is **no wiring from the IWR6843's per-frame range-rate into this grid** anywhere in `src/`; the only place a radar-anchored per-frame range appears is as a formula in the not-yet-implemented `2026-08-28-codex-brief-template-alignment.md` spec (`range_mm(f) = 1581 − range_rate_ms × 1000 × (f_contact − f) / fps`). The report's own recommendations table (§07) lists "Radar range model + rotation-axis constraint — Implemented; orientation still fails" for work dated 2026-08-27, but that implementation is not present in this branch's `fit.py` — it most plausibly lives in the `falsification/` scripts kept on `feat/silhouette-poc` (explicitly excluded from this branch per `docs/clubface-impact-location.md`: "Deliberately excluded from this branch... the superseded synthetic-phase evaluation... They remain on the fork's `feat/silhouette-poc` branch"). **So: yes, `fit_sequence` in this branch still effectively treats range as close to constant** (a 200mm-wide 3-point grid around the ball's own range, not a 529mm swing-to-impact traverse), contradicting the "Implemented" status claimed in the report for the branch it's read alongside.

**(e) `detect_face_plane` is unfixed in code despite being flagged as the report's headline defect.**
`mesh.py:318-399` has no comment, no TODO, and no discriminator between "cavity rim" and "striking face" beyond the aspect/flatness/extremity geometry heuristic that the report shows picks the wrong one on a cavity-back iron. The interim workaround (`angles.py`'s `square_pose()`) is a seed-only patch — it does not change what `detect_face_plane` reports as loft/lie if that function is called directly elsewhere. Tier 2 in the report ("hours") has not been picked up.

## 3. Single most likely blocker

**Segmentation precision, not the fitting algorithm, not the sensor, not the fusion architecture.**

The report's own numbers make this unambiguous: 1px of mask boundary error ≈ 10° of face angle; the first 5° of face angle changes the rendered silhouette by 0px; two independently-failing objective functions (IoU, chamfer) converge to poses 12.7° apart from identical seeds. Every other candidate blocker (wrong camera constants, constant-range assumption, backwards mesh frame, acoustic-lag bug) has either been fixed already or is dwarfed in magnitude by this one. Even a perfect fitting algorithm cannot beat noise this large, and the report says so explicitly ("Recommendation: no further effort on the objective function"). The two follow-ups queued to fix this — a learned segmenter (`2026-08-28-clubhead-segmentation-labelling-spec.md`) and polarity-aware template alignment (`2026-08-28-codex-brief-template-alignment.md`) — are the right response, but neither has produced a result yet: the labelling spec requires ~400 hand-labelled frames not yet made, and `outline_align.py` doesn't exist (only its test stub does).

**Cheapest experiment to confirm/refute that this is really the binding constraint:** run the outline-alignment spike (`2026-08-28-codex-brief-template-alignment.md`) before the segmentation-labelling spec. It needs zero new labels (uses the existing mesh + radar range + shaft-angle-from-image), is a translation-only 2-parameter search (not 6-DOF), and its own pre-registered checks (two-frame consistency ≤1px on ≥80% of shots, shot-014 hand-mark agreement within 1.5px, residual median ≤1.0px) will directly show whether pinning range/lie/loft externally and only translating in image space clears the noise floor that sank the contact-edge threshold rules. If it also fails availability/consistency at rates similar to the contact-edge spike (3/21, 1/21), that is strong evidence the blocker is the raw pixel data (motion blur, exposure, plate scale) rather than the estimator — and would justify prioritizing the 1280×800 1:1 capture (Tier 3) over the learned segmenter (which trains on the same noisy 320×200 pixels). If it clears its thresholds, segmentation-by-threshold specifically (not resolution) was the problem, and the learned-segmenter investment is justified.

## 4. Three things to stop, three things to start

**Stop:**
1. **Stop iterating on 6-DOF silhouette pose objective functions.** The report already says this in its own words. Any further chamfer/IoU/hybrid metric work on the current 320×200, ~30px-clubhead data is re-deriving a conclusion that's now confirmed twice (literature in July, real data in August).
2. **Stop letting "Implemented" appear in a status table for work that isn't in the branch being read.** The radar-range-model / rotation-axis item is marked "Implemented" in the report's recommendations but isn't in `src/` on `feat/clubpose-fit` — it's on `feat/silhouette-poc`. This is a paper-trail problem, not a code problem, but it's exactly the kind of gap that let the 6.0-frame acoustic-lag error propagate through months of work before being caught. Every status claim should name the branch/commit it's true on.
3. **Stop leaving dead-but-wrong presets (`A0`, `fx=1033`) sitting in a shared module (`projection.py`) next to the correct ones.** It costs nothing to delete or clearly quarantine `camera_presets()` now that nothing in `src/` calls it; leaving it is exactly the setup for a future silent regression the moment someone reaches for "the camera preset" instead of `measured_camera()`.

**Start:**
1. **Start with the outline-alignment spike, not the segmentation-labelling spec.** It's cheaper (no labels), tests the load-bearing hypothesis directly, and its pass/fail result changes what the (more expensive) labelling effort should even target.
2. **Start wiring the radar per-frame range into `fit.py`'s actual grid** (or retire `fit_sequence`/`fit_frame_6dof` in favor of the translation-only approach entirely) so the report and the code agree about what's implemented where. Right now `CAMERA_CENTER_WORLD` (209.55mm/1575mm) and `range_grid_mm=(1481,1581,1681)` are stale relative to both the measured tape values and the radar range-walk finding.
3. **Start the Trackman-alongside session.** It is Tier 1 in the report for good reason: `estimate_chained_delivery`'s attack-angle/club-path numbers (item #9 above) are the most consequential unvalidated figures in the whole project, frozen against a 17-shot replay with no ground truth, and everything downstream (comparator claims against Trackman 4) depends on closing that gap.
